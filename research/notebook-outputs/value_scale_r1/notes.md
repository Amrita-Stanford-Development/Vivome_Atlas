# R1 notes, written after the run

The report beside this file is generated by
`research/notebooks/value_scale_r1.py`. These notes explain it against
`valuescale/bank/expectations/r1.json`, which was written before R1's code
and before either check ran on any table (`6a101d8`), and was not edited
after the run.

## What R1 is, in plain words

**Where it fits.** B7's sealed test contradicted the detector's promise for
small log tables. Three of its misses came from faulty test tables that B3's
walk should never have kept: two empty ones (PXD022054 and PXD047898) and a
log2 table labelled linear (PXD066316). Protein v2
(`research/value-scale-v2-plan.md`) reworks the detector and draws a fresh
calibration and test. R1 adds the checks the walk lacked, before any new
table is drawn.

**What it does.**
- **An empty table is refused,** as a walk outcome of its own, `empty`. A
  table is empty when no value is observed: every entry is missing,
  infinite or 0. Such a table says nothing about its scale, so refusing it
  cannot bias the labels. The check comes after the walk's size checks and
  before the label, so every other outcome stays as it was.
- **A table labelled linear whose values look log is flagged** (`looks_log`):
  99% of its observed values are under 64. A log2 table's values stay well
  under it; a linear table's spread over several decades above it. The
  record keeps the value range (smallest, median, 99th percentile,
  largest). The label is not changed and nothing is refused. The hand
  audit's sample takes every flagged table, besides its seeded 20%, and a
  flagged table's packet shows its range beside its headers and methods.
  The auditor keeps the label, relabels the table from its provenance, or
  excludes it.
- **The service and the Atlas page refuse an upload with no observed value**
  (the plan: "checked in the same step and fixed test first if needed").
  It was needed, so the fix was made test first (below).

## What was built (test first, `56421b1`)

- `valuescale/corpus/draw.py`: `empty`, `looks_log`, `LOG_CEILING = 64`
  (B7's post hoc read used the same), and the new outcome and flag in
  `visit`. The docstring now names the three facts of a table's values the
  walk reads: whether any is observed, the label's refusal of a negative
  value, and the flag's range. None of them is a detector statistic.
- `research/notebooks/value_scale_corpus.py`: `audit_sample` takes every
  flagged table; `_packet` builds a packet, with a flagged table's values
  section.
- `service/pipeline/validation.py`: `validate_values` refuses a table whose
  every entry is empty, infinite or 0, with a 400 and the sentence
  `NO_VALUES`. It runs after the orientation and the cell count.
- `web/js/atlas/file-check.js`: `checkLimits` turns such a file down before
  anything is sent, in the service's words (`NO_VALUES`). The file is then
  not ok, so the pop-up does not ask about its values and Project stays off.

Each test was seen failing first: the walk's and the audit's
(`valuescale/tests/test_draw.py`), the service's
(`service/tests/test_validation.py`, `service/tests/test_app.py`) and the
page's (`web/tests/atlas-file-check.test.js`).

**What the service did before** (a scratch probe on 2026-11-10, before
`r1.json`; a 200-protein, 25-cell table through the pipeline, protein):
- every entry empty or NA: a 200 reply, every cell without an answer, under
  both ways to read the values;
- every entry 0, under the calibrated method (on the branch): a 200 reply,
  every cell without an answer (verdict "unlike either", read linear, so
  every 0 missing);
- every entry 0, under the median rule (the live one): a 200 reply with a
  label for every cell. The rule reads such a table as log, so every 0 stays
  a value, and every cell is the same constant profile.

The site's check passed such a file: its facts line said "Every value is
empty." (or that 100.0% are 0), and a protein file was asked raw or log.

## What it shows

- **The two checks catch exactly the faulty tables B7 found, and nothing
  else** among B3's 457. Had they run in B3, the test would have kept
  neither empty table, and the audit would have read PXD066316's values
  beside its headers.
- **The flag is cheap on real linear tables.** It fires on none of the
  bank's 28. The plan named PXD064083's tables (median about 7) as the
  kind an automatic refusal by value range would drop. The rule does not
  fire on them: a raw table with a small middle value still has its
  highest values far above 64. A scratch look after the run (not part of
  `report.json`) put the lowest 99th percentile among the bank's linear
  tables at 131.6 (furtwangler_batchcorr_norm, median 10.6), and
  pxd064083_t's at 457.7. The plan's reason for an audit rather than a
  refusal still stands (a label is a matter of provenance, and a linear
  table can be small), but the bank holds no table that shows it.
- **The audit's extra load at R4 should be small.** On B3's walk the flag
  would have added one table, PXD066316, which the seeded 20% had not
  drawn. PXD022054 was audited (among the tables the third visit added),
  and its label agreed: a packet showed headers and methods, never values,
  so nothing in it said the table was empty.

**Two things to know.**
- The run reads each kept table as the walk stored it (`table.npz`, float32).
  The walk itself checks the parser's values: float32 from the service's
  parser, float64 from `tables.py`'s readers. The ranges can differ in the
  seventh digit; no decision can.
- B3's records are unchanged. `walk.jsonl` and `audit.json` are v1's
  record; the new outcome and flag apply to R4's walk over the reserve.
