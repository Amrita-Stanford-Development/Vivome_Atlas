## What B5 is, in plain words

**Where it fits.** Phase B builds the automatic raw-or-log detector for
protein uploads (`research/value-scale-plan.md`). B4 set its thresholds.
B5 puts it in the service and asks the uploader on the site
(`research/value-scale-b5-design.md`). B6 checks the assembled service.
B7 scores the sealed test once, and then, with the owner's OK, the site
and the service go live together. B5 is not deployed.

**What changed in the service.** When a protein request does not say how
its values are scaled, Stage 0 now asks the detector (`valuescale.detect`),
not the median rule:
- "linear" or "log" is the reading;
- "can't tell" or "unlike either" is read as raw (B1's cheaper mistake).

Under a log reading, a 0 is not measured, unless the request says
otherwise or the table is centred (at least 1% of its observed values
negative). A table the service would itself read as raw that holds
negative values is refused, in clear words. The reply names the check's
verdict, what a 0 was read as and the check's report. RNA keeps the median
rule. The scripts of the tests whose protocols were frozen under the
median rule keep it by name.

**How the run checks it.** The run takes the 30 bank tables that Phase A
traced. Each is sent through v4.1 twice in the same process: under the
calibrated method (the default), and under the median method, the rule
before B5, as the baseline. Each table is also sent as RNA both ways, and
a few through the app's handler.

## The failed row: the warning

The warning says a table is farther from the detector's design tables
than any of them is from the rest. In B4, the bank's verdicts were scored
with each table's own deposit left out of the model
(`research/notebooks/value_scale_calibrate.py` `bank_verdicts`, through
`value_scale_method.fit_models`). That way a design table is judged as a
stranger would be. The shipped detector uses the calibration's model,
fitted on every design row. pxd043355_pd's deposit is one of them, so the
detector has seen it.

A probe after the run, outside the report, confirms it (a scratch script,
not kept). On the traced pxd043355_pd table:
- **The shipped detector:** linear, typicality 0.74 for the linear
  reading, no warning.
- **The model fitted without PXD043355:** linear, typicality 0, the
  warning.

So the service is right, and b5.json's prediction was wrong. It took B4's
left-out warning for the shipped detector's. The same holds for every
bank table: each is a design table of the shipped detector, so none is
unlike them. The verdicts agree either way. The warning's own behaviour
on unseen tables is B4's finding, and B7 measures it on the sealed test.
