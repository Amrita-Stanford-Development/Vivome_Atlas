Raw or log

A protein table can hold its values raw or as logs, and the service has to know which before it reads a single cell. This topic tells how VivOME finds out, what we did to build and test that, and what we found.

The problem: two ways to write one table

A protein table has one row per protein and one column per cell. Each number says how much of that protein the instrument saw in that cell.

Software writes those numbers in one of two ways. Raw values, also called linear, are the amounts themselves: twice the protein, about twice the number. Log values are the same amounts after taking a logarithm, which turns multiplying into adding, so each doubling adds the same step. Both are common, and a file rarely says which it holds.

The service needs log values. Its first step, Stage 0, decides which kind it was given and takes the log of raw values. Read a log table as raw and it takes a second log; read a raw table as log and it takes none. Nothing fails loudly: every answer after it is quietly a little off.

How much, we measured in B1 by reading the bank's tables the wrong way on purpose. For a typical log table read as raw, of its cells' best guesses changed. For a typical raw table read as log, changed.

The old rule

Before this work the service used one rule for every table: no negative value and a median above means raw. It is still the rule on the live site. The trouble is that size depends on units, and units differ between instruments and software; many raw tables are rescaled to small numbers. In Step 1 the rule misread of the bank's raw tables. PXD064083 was among them: its values are raw, with a median of about .

For the curious: why the log's base does not matter

Before the model sees a table, the service turns each gene's values into z-scores: it takes away the gene's average and divides by its spread. Log values in another base differ only by a fixed factor, and a number added to every value only moves the average, so both vanish in the z-score. One question is left: does this table still need a log?

How the detector reads a table

The detector looks at the shape of the numbers, never at their size.

First, two gates

Some tables settle the question by definition, so plain rules, the gates, come first:

  • a real share of negative values: an amount cannot be negative, so the values are already log, or centred;
  • every value a whole number, with enough different values: these are counts, so raw.

A few stray negatives are set aside as missing, so they cannot trip the first gate. Some tables the detector will not judge, and it says why: fewer than cells, too few to tell; each protein divided by, or centred on, its own level; or no value missing at all, since the table may have been filled in. Each of those is “can't tell”.

Then, the shape

It measures things that do not change when every value is multiplied by the same number, so units and rescaling cannot fool it. These are scale-free measures:

  • how lopsided each cell's values are: raw values have a long tail of large amounts, log values sit closer to even;
  • how far the top values reach past the middle ones;
  • whether a protein's spread grows with its level. In raw values it does, because measuring errors are a share of the amount; after a log it does not.

A probability, then the answer

A simple model, fitted on the bank's tables and their variants, turns those measures into a probability that the table is raw, and one that it is log. Each reading whose probability clears its threshold joins the answer:

  • raw only: the service takes the log;
  • log only: the values are used as given;
  • both: “can't tell”;
  • neither: “unlike either”.

On “can't tell” and “unlike either” the service reads the table as raw and says so, because B1 found it the cheaper mistake.

For the curious: the measures and the model

The measures are each cell's Bowley and Moors skewness, a tail ratio (how far the top reaches past the middle, against the spread of the middle half), and the rank correlation between each protein's level and its spread, with missing values ranked lowest. Side measures include the share of values missing. The model is a ridge logistic regression.

A typicality score, the distance to the nearest design tables, was planned as part of the score. In B4, before any calibration score was computed, it became a warning only: it would have set one threshold to zero (a protocol amendment).

How sure it is: the promise

In plain words: for each kind of table, raw or log, and each size group, the right reading is left out of the answer at most of the time, and we are sure of that. This is the promise.

Left out means a miss: the answer is the wrong reading alone, or “unlike either”. “Can't tell” is not a miss, since the right reading is still in the answer.

Size groups

Small tables are harder to read, so the promise is kept for each size group on its own: S1, from to cells; S2, from to ; S3, from to . S3 had too few tables, so it joins S2 as S2+S3. A table with more cells than that uses S2+S3's thresholds, without the promise.

How a threshold is set

Take the calibration tables whose answer is log and score each one: the model's probability that it is log. Sort the scores from low to high and take the k-th smallest as the log threshold. A new log table then falls below it, and is missed, only about as often as the calibration tables did. The raw threshold is set the same way, from the raw tables.

Why a group needs tables

Say the smallest score is the threshold. The promise then fails only if more than of log tables score lower, and yet every calibration table happened to score above. With tables, the chance of that is under . With fewer, no threshold can keep the promise. More tables allow a larger k, so a lower share of tables is missed by chance.

The thresholds in use

  • S1, from calibration tables, with k : raw , log .
  • S2+S3, from tables, with k : raw , log .
For the curious: conformal prediction and the umbrella k

This is split conformal prediction with one threshold per class and size group. The k is the umbrella order statistic of Neyman–Pearson classification: the largest k for which the chance of a miss rate above α is at most δ. With the smallest score as the threshold, that chance is one minus α multiplied by itself n times, and is the smallest n that brings it to δ or below.

Where the tables came from

The bank

The bank came first, in Step 1: real public tables, each with its answer known from its documentation, chosen to cover the cases the detector must handle: different software and instruments, raw values on a small scale, centred and filled-in log tables. Every step was checked on the bank before the next began.

The corpus

Calibration and the sealed test needed many more tables, drawn by rule, not by hand. This is the corpus, collected in B3:

  • the frame: public human deposits in PRIDE and MassIVE announced from 2020-01-01 to 2026-10-31, put in a fixed random order before any was opened;
  • each deposit goes to calibration or to the test by a hash split of its accession;
  • walking that order, we listed deposits and took each one's first table that looked usable; had none;
  • each table's label, raw or log, came from its software's documentation before any statistic was computed (a provenance label), and a hand audit of a sample agreed on of ;
  • tables were kept, and after the audit: for calibration and for the test;
  • the other deposits were never listed. They are the reserve, kept for a fresh test.

No real log table

Not one table in the corpus was labelled log by its documentation. So we make each raw table's log copy ourselves, a constructed log, and the log side of the promise is tested on those. That is a stated limit of this work.

The clean-up

The walk met faults in our own reading code: unusual line endings, column names, file encodings, decimal commas. We fixed them, each with a test written first, and then visited the tables they touched again, twice. The fixes went live on 2026-11-07.

For the curious: how the draw was kept fair

The order and the split were fixed before any table was opened, so nobody could steer which deposit landed where. Quotas by number of cells kept each size group filled. The audit was done by AI helpers under a rubric committed before any table was shown to them, and Claude read every disagreement again, with a share of the agreements.

How we tested it

Sealed, then scored once

The test tables were not scored until the method was fixed. Before the scoring we wrote down what we expected, in a file committed first. The scorer writes a mark before it reads any test table and another after, and refuses to run while either exists. So the sealed test runs once, and nobody can try again until it looks good.

Checking the promise

For each group we count the misses and ask: what is the smallest miss rate this count fits, at confidence? That is the lower bound. If even the lower bound is above , the promise is contradicted.

A count a little above the promise can still fit it. misses of is , but its lower bound is , under : a table set that size could miss that many by chance while keeping the promise.

Against the old rule

On the raw test tables, we asked whether the detector misreads fewer than the old rule. McNemar's test answers that from the tables where the two disagree.

For the curious: the statistics

The bounds are one-sided Clopper–Pearson bounds. The McNemar test is exact and one-sided. The protocol and its amendments fixed all of it before the test was opened.

Words

The words this topic uses, in plain language, from A to Z.

The bank
The real public tables we gathered in Step 1, each with its answer, raw or log, known from its documentation. Every later step was checked on them before the next one began.
Best guess
The cell type the model ranks first for a cell. When a table is read the wrong way, some best guesses change: that is how we measured what a wrong reading costs.
Calibration
Setting the thresholds from tables whose answer is known, so that the promise holds. The calibration tables and the test's are kept apart: a deposit is in one or the other, never both.
“Can't tell”
The answer when both readings clear their thresholds: the table could be either. The service then reads it as raw, says so, and the uploader can choose the other reading and send it again.
Centred table
A log table with each protein's average taken away, so its values sit around zero and many are negative. A zero in such a table is a real value.
Constructed log
A log table we make ourselves by taking the log of a raw table. The corpus held no public table labelled log, so the log side was tested this way.
Corpus
The large set of public tables collected in B3 for calibration and the sealed test.
Deposit and accession
A deposit is one study's data in a public store. Its accession is its name there, such as PXD064083.
Design data
The tables the method was built and fitted on: the bank and its variants.
Development data
Tables we may look at, try ideas on and change things for. A test, once scored, becomes development data.
Foreign table
A table that is neither raw nor log, such as z-scores, present-or-absent marks or ranks. Used to check that the detector answers “unlike either” when it should.
Frame
The full list of deposits the corpus could be drawn from, put in a fixed random order before any was opened: deposits.
Gate
A plain rule checked before any statistics, for cases that settle the answer by definition: a real share of negative values means log; whole-number counts mean raw.
Hand audit
A second reading of the documentation behind a sample of tables, to check their labels. In B3 it was done by AI helpers under rules written before they started; Claude read every disagreement again, and a share of the agreements.
Hash split
How each deposit was sent to calibration or to the test: by a fixed scramble of its accession, so nobody chose, and a deposit always lands on the same side.
The k-th smallest
How a threshold is set: sort the calibration tables' scores from low to high and take the one in place k. The number of tables fixes k, so the promise holds.
Log values
Numbers after taking a logarithm. A log turns multiplying into adding: each doubling of a protein adds the same step. Many tools write log values, most often log2.
Lower bound
The smallest miss rate a test result fits, at confidence. If even that is above , the promise is contradicted.
Marks
The two files the test scorer writes: one before it reads any test table, one after it scores them. While either exists, it refuses to run again.
McNemar's test
A test for two methods judged on the same tables. It looks only at the tables where they disagree, and asks whether one wins those more often than chance would.
Median
The middle value: half the values are below it and half above.
Missing value
A protein that was not measured in a cell. Some tools leave the place empty, others write a zero, so what a zero means has to be known too.
The old rule (median-50)
The rule the service used before this work, and still uses on the live site: a table with no negative value whose median is above is read as raw, and any other as log.
PRIDE and MassIVE
The two big public stores of proteomics data our deposits come from.
Probability
Here, the model's estimate, between zero and one, that a table is raw, and that it is log.
The promise (α and δ)
The detector's guarantee: for each kind of table and each size group, the right reading is left out of the answer at most α of the time (here ). δ is how often, at most, the calibration could have been unlucky enough to break that (here ), so we are sure of it.
Provenance label
A table's answer, raw or log, taken from what its software's documentation or its paper says about the file, and fixed before any statistic is computed on it.
Raw (linear) values
The numbers the software writes for how much of each protein it saw, before any log is taken: twice the protein gives about twice the number. Also called linear intensities.
Real log
A log table written by its own software or authors, not made by us. The bank holds a few; the corpus found none.
Rehearsal
A dry run of the test scorer on the calibration tables, to check its code before the one real scoring.
Reserve
The deposits of the frame that B3 never listed. They stay unopened, for a fresh test.
Scale-free measure
A number about a table's shape that does not change when every value is multiplied by the same number, or, for log values, when the same number is added to each. Units cannot fool it.
Sealed test
Tables kept unopened until the method is fixed, then scored once, against expectations written before.
Size group (stratum)
Tables grouped by their number of cells (columns): S1 from to , S2 from to , S3 from to . S3 had too few tables of its own, so its tables join S2's for calibration, as S2+S3.
The sparse-log gap
The detector's weak point: a log table with many values missing can look raw to it. B4 saw it on the bank, and B7 found it in the test.
Spent test
A test that has been scored. Once we have seen its answers it cannot test again, so it becomes development data.
Stage 0
The service's first step with an uploaded table: deciding raw or log, and taking the log when the values are raw. Every later step works on log values.
Threshold
The lowest probability a reading needs to stay in the answer. Each reading in each size group has its own, set by calibration.
Typicality warning
A note in the reply when a table is farther from the tables the detector was built on than any of them is from the rest. Since B4 it no longer changes the answer.
“Unlike either”
The answer when neither reading clears its threshold. The service reads the table as raw, with a warning.
Variant
A changed copy of a table, with a known answer: multiplied, logged, cut to fewer cells, with values taken away. Variants check that the measures behave.
z-score
A value minus its gene's average, divided by its spread. The service z-scores every gene before the model sees it, which removes any log base.
